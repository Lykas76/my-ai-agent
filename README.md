# my-ai-agent
Персональный AI-агент для смартфона с памятью, задачами и автоматизацией.

Текущее состояние: Блоки 1–4. Все `POST /requests` требуют Bearer-токен;
публичным остаётся только `GET /health`. Инструкция создания пользователя и выдачи
токена приведена в разделе «Блок 4» ниже. Режима обхода аутентификации нет.

## Этап 1: локальное ядро

Python 3.10+; обязательных сторонних зависимостей нет. Внешние сервисы,
LLM и управление Android пока не подключены.

### Структура

- `assistant/`: модели Request/Response и маршрутизация явных команд.
- `memory/`: протокол Memory и SQLite-хранилище ключ/значение.
- `tools/`: реестр доверенных обработчиков с запретом выполнения по умолчанию.
- `api/`: локальный HTTP API, привязанный к 127.0.0.1.
- `tests/`: тесты компонентов и HTTP с временными базами.

### Запуск и проверка

Из корня проекта:

```console
python -m api.server
python -m unittest discover -s tests -v
python -c "import config, assistant.core, assistant.models, memory.base, memory.sqlite, tools.registry, api.server"
```

`GET http://127.0.0.1:8000/health` возвращает `{"status":"ok"}`.
Команды передаются через `POST /requests` с `Content-Type: application/json`
и `Authorization: Bearer <TOKEN>` (подставьте выданный локально токен):

```json
{"action":"ping"}
{"action":"memory.put","parameters":{"key":"note","value":"Позвонить завтра"}}
{"action":"memory.get","parameters":{"key":"note"}}
{"action":"memory.delete","parameters":{"key":"note"}}
{"action":"tool.run","parameters":{"name":"example","arguments":{}}}
```

Ответ: `{"ok":true,"result":"pong","error":null}` для ping.
Неизвестные команды и ошибки параметров дают HTTP 400; запрещённые инструменты — 403.
Неизвестный путь — 404, неверный Content-Type — 415, недопустимый размер тела — 413.
Максимальный размер тела — 64 КиБ. Инструментов в запущенном API пока нет:
`tool.run` всегда отклоняется, пока доверенный код не зарегистрирует обработчик
через `ToolRegistry.register(Tool(..., permission="read"), enabled=True)`
и не выдаст пользователю точное разрешение на этот инструмент.

### Конфигурация

`.env.example` содержит только имена переменных с пустыми значениями.
По умолчанию база находится в `data/assistant.sqlite3`, порт — 8000.
Можно задать `ASSISTANT_DB_PATH` и `ASSISTANT_PORT` через окружение процесса.
Пустые значения этих двух переменных используют значения по умолчанию.
Существующие `BOT_TOKEN` и `OPENAI_API_KEY` сохранены, но ядро их не использует.
Если python-dotenv уже установлен, config.py продолжает загружать `.env`;
без него используйте переменные окружения. Установка для этапа 1 не нужна.
Импорт модулей не создаёт базу и не запускает сервер.

### Границы и расширение

Это прототип для одного локального пользователя. HTTP-сервер последовательный,
SQLite-соединение используется в его потоке. Health-check подтверждает работу HTTP,
а не доступность внешних сервисов. База не зашифрована; не храните в ней токены.
API проверяет Bearer-токены, но остаётся локальным HTTP-прототипом без TLS.
Не публикуйте его через прокси или туннель. Запросы с Origin отклоняются; CORS не включён.
Реестр — список разрешённых обработчиков, а не песочница для недоверенного кода.

Следующие адаптеры Android, Telegram и голоса должны преобразовывать входные данные
в Request и вызывать Assistant.handle. Адаптеры Google Drive, Gmail и Calendar
могут реализовать инструменты за интерфейсом реестра. Перед их подключением нужны
идентификация пользователя, разрешения, подтверждение опасных действий и хранение
учётных данных вне памяти. Реализация Memory может быть заменена без изменения ядра.
Диалоговый интерфейс с локальным тестовым провайдером реализован в Блоке 2 ниже.
Подключение внешних каналов и реальных AI-провайдеров остаётся отдельным этапом.

## Блок 2: диалоговое ядро

Новая команда `dialogue` доступна через тот же `POST /requests`.
Существующие команды и формат внешнего Response сохранены.

```json
{"action":"dialogue","parameters":{"message":"Привет!"}}
{"action":"dialogue","parameters":{"message":"Что ты помнишь про кофе?"}}
{"action":"dialogue","parameters":{"message":"Расскажи про кофе","history":[{"role":"user","content":"Привет"},{"role":"assistant","content":"Здравствуйте"}]}}
```

Если ранее выполнен `memory.put` с ключом `кофе` и значением `Без сахара`,
ответ на второй запрос имеет вид:

```json
{"ok":true,"result":{"reply":"Нашёл в памяти:\nкофе: Без сахара","intent":"recall","context_keys":["кофе"],"tool_used":null},"error":null}
```

### Архитектура одного хода

1. `Assistant` передаёт параметры команды в `DialogueHandler`.
2. `IntentDetector` различает greeting, recall, tool и chat по локальным правилам.
3. Для recall/chat выполняется поиск релевантных записей памяти.
4. Явная команда `/tool NAME {JSON}` передаётся в существующий `ToolRegistry`.
5. `AIProvider.generate(ProviderRequest)` получает текст, intent, контекст,
   историю и результат инструмента; возвращает текст ответа.

`assistant/providers.py` задаёт протокол провайдера и типизированные входные данные.
По умолчанию используется `LocalProvider`: детерминированный тестовый обработчик,
без сети, AI-модели и API-ключей. Для подмены в доверенном коде передайте
`Assistant(memory, registry, provider=my_provider)`. Провайдер возвращает только
текст и не получает доступ к памяти или реестру через ProviderRequest.
Текст ответа провайдера не интерпретируется как команда.

### Память и история

`memory/search.py` задаёт отдельный протокол SearchableMemory и модель MemoryEntry.
SQLite реализует поиск по словам в ключах и значениях с нормализацией регистра
и ё/е, исключением служебных слов и повышенным весом совпадения в ключе.
Равные результаты сортируются по ключу. Изменение схемы существующей базы не нужно.
Адаптеры старого интерфейса Memory без search продолжают работать с пустым контекстом.

Поиск лексический: без эмбеддингов, синонимов и распознавания словоформ; использует
только текущую реплику, а не историю. Он просматривает все записи и предназначен
для небольшой локальной базы. Запрос без значимых слов возвращает пустой контекст.
В провайдер передаются максимум 5 записей: до 200 символов ключа и 1000 символов
значения каждой. Для приветствий и инструментов память не извлекается.

В режиме Блока 2 история передаётся клиентом явно: максимум 20 сообщений с ролями user/assistant,
до 4000 символов на сообщение; текущая реплика также ограничена 4000 символами.
Общий HTTP-лимит 64 КиБ остаётся в силе. Переданная клиентом история не считается
доверенной командой и не запускает инструменты. Начиная с Блока 3 HTTP API сохраняет
новые реплики в сессии и автоматически восстанавливает их; подробности ниже.
LocalProvider принимает историю для проверки контракта, но не делает выводов из неё.
Запись фактов в память пока выполняется только отдельной командой memory.put.

### Инструменты и ошибки

Пример подключения безопасного локального инструмента в доверенном Python-коде:

```python
from assistant.core import Assistant
from assistant.models import Request
from memory.sqlite import SQLiteMemory
from tools.registry import Tool, ToolRegistry

registry = ToolRegistry()
registry.register(Tool("echo", lambda arguments: arguments.get("text", ""), permission="read"), enabled=True)
with SQLiteMemory(":memory:") as memory:
    user = memory.security.create_user()
    memory.security.grant(user.user_id, "echo", "read")
    assistant = Assistant(memory, registry).for_user(user)
    response = assistant.handle(Request("dialogue", {"message": '/tool echo {"text":"Привет"}'}))
    print(response.result["reply"])
```

В API по умолчанию реестр по-прежнему пуст: `/tool android` и любые другие
незарегистрированные или выключенные инструменты отклоняются. Поле enabled
в аргументах не меняет разрешения. Контекст памяти, история и ответы провайдера
никогда не запускают инструменты. Нечёткие просьбы вроде «запусти echo» остаются chat.

Ошибки провайдера, памяти и обработчика инструмента возвращаются как `ok: false`
(HTTP 400 в существующем API), без внутреннего текста исключений. Автоматического
повтора нет: инструмент мог уже выполнить действие до ошибки. Результат инструмента
должен быть строкой; в провайдер передаются первые 4000 символов. Транзакционной
отмены инструментов и гарантий идемпотентности пока нет.

## Блок 3: постоянные сессии и история

В той же SQLite-базе добавляются таблицы `sessions` и `session_messages`, а также
индекс истории по пользователю, сессии и порядковому номеру сообщения.
Существующая таблица фактов `memory` сохраняется без изменений и миграции данных.
`memory/sessions.py` содержит модель Session, протокол SessionStore и реализацию
SQLiteSessionStore. Соединение и срок жизни хранилища совпадают с SQLiteMemory.

Сессия содержит user_id, session_id, created_at и updated_at (UTC, ISO 8601).
ID новой сессии генерируется через UUID4. Порядок сообщений задаёт message_id,
поэтому совпадение времён не влияет на порядок. История восстанавливается после
повторного открытия файла базы без каких-либо данных в оперативной памяти клиента.

### Запросы API

Создать сессию аутентифицированного пользователя (добавьте заголовок Bearer):

```json
{"action":"dialogue","parameters":{"message":"Привет!"}}
```

В `result` сохраняются прежние поля reply, intent, context_keys, tool_used и добавляются
user_id, session_id, created_at, updated_at. Для продолжения передайте возвращённый ID:

```json
{"action":"dialogue","session_id":"ID-ИЗ-ПРЕДЫДУЩЕГО-ОТВЕТА","parameters":{"message":"Продолжим"}}
```

Идентификаторы можно также передавать внутри parameters. Передача одного и того же
поля одновременно на верхнем уровне и в parameters отклоняется, даже если значения
совпадают. Для действий, отличных от dialogue, идентификаторы сессии не принимаются.

HTTP API определяет user_id по токену; переданный клиентом чужой user_id даёт 403.
Если session_id отсутствует,
каждый успешный запрос создаёт новую сессию и возвращает её ID. Для продолжения
нужно сохранять и передавать ID вместе с тем же user_id. Неизвестный ID не создаёт
сессию с выбранным клиентом именем: запрос отклоняется.

ID должен содержать от 1 до 64 ASCII-букв, цифр, точек, дефисов или подчёркиваний
и начинаться с буквы либо цифры. Пустые строки, null, пробелы и другие типы запрещены.
Для неизвестной сессии и сессии другого пользователя возвращается одна ошибка
`Session not found`, без раскрытия владельца или истории. Ошибки дают HTTP 400;
внутренние сообщения SQLite клиенту не передаются.

### История и совместимость

При продолжении сессии история загружается автоматически только по её паре
(user_id, session_id). Непустое поле history в таком запросе отклоняется: клиент
не может заменить сохранённую историю. При создании новой сессии прежнее поле
history остаётся доступным как временный контекст, но не записывается в базу.
Сохраняются только новая реплика пользователя и фактический ответ провайдера.

В прямом Python API `Assistant.handle` запрос dialogue без обоих идентификаторов
сохраняет поведение Блока 2: не создаёт сессию, принимает явную историю и возвращает
прежний набор полей. Передайте user_id, чтобы включить постоянную историю.
Старые адаптеры Memory по-прежнему поддерживаются в этом режиме; для сессий им нужен
SessionStore, который можно передать через `Assistant(..., sessions=store)`.

Успешная пара сообщений и обновление времени сессии записываются одной транзакцией.
Новая сессия создаётся в этой же транзакции после получения ответа. Ошибка провайдера
не оставляет пустую новую сессию или половину диалога. При ошибке сохранения история
откатывается, но ранее выполненный инструмент отменить нельзя: автоматического
повтора нет, и ошибка предупреждает об этом. Failed/pending-сообщения пока не хранятся.

### Ограниченный контекст

Политика `assistant/history.py` детерминирована:

1. Выбирается окно последних сообщений только текущей сессии.
2. Приоритет имеют два самых последних сообщения, затем совпадения слов текущего
   запроса, затем более свежий message_id. Регистр и ё/е нормализуются.
3. Применяются лимиты числа сообщений и суммарного числа символов; каждое сообщение
   дополнительно ограничено первыми 4000 символами. При нехватке бюджета текст
   обрезается. Отобранные сообщения передаются провайдеру в хронологическом порядке.

Лимиты задаются окружением при запуске `python -m api.server`:

| Переменная | По умолчанию | Допустимые значения |
|---|---:|---|
| ASSISTANT_HISTORY_MAX_MESSAGES | 20 | 1–100 |
| ASSISTANT_HISTORY_MAX_CHARS | 8000 | 1–100000 |
| ASSISTANT_HISTORY_CANDIDATES | 100 | 1–1000, не меньше MAX_MESSAGES |

Пустые значения используют настройки по умолчанию. Неверная конфигурация не позволяет
запустить сервер. В Python-коде используется `Assistant(..., history_policy=HistoryPolicy(...))`.
Лимит символов относится к содержимому исторических сообщений: текущая реплика,
контекст памяти и результат инструмента имеют собственные прежние ограничения.
История в базе не обрезается, ограничивается только контекст провайдера. Поиск
релевантности лексический; отбор может включить отдельные сообщения без полной пары.

### Ограничения и следующий этап

Начиная с Блока 4 HTTP API определяет пользователя по токену. История и факты
HTTP-клиентов изолированы. Прежняя таблица memory сохранена для доверенного локального
кода и не видна аутентифицированным HTTP-клиентам автоматически. История не индексируется поиском фактов и
не может запускать инструменты. LocalProvider получает историю, но пока не рассуждает
на её основе; тестовый провайдер проверяет передачу контекста.

Шифрование, удаление/срок хранения истории, идемпотентность запросов и координация
нескольких процессов пока отсутствуют. HTTP-сервер остаётся последовательным.
Аутентификация, персональная память и разрешения реализованы в Блоке 4.
Следующий этап — полноценный протокол подтверждения действий перед внешними каналами.

## Блок 4: локальная безопасность

### Пользователи и токены

`security/store.py` добавляет таблицы users, api_tokens, tool_permissions и security_audit.
Пользователь имеет внутренний user_id (по умолчанию UUID), статус active/disabled,
created_at и updated_at в UTC. Email и телефон не требуются.

Токен состоит из открытого идентификатора token_id и 32 случайных байтов в URL-safe
кодировке. В SQLite сохраняются token_id, user_id, SHA-256 полного токена, дата выдачи
и признак отзыва. Секретная часть и полный токен не записываются. SHA-256 применяется
к случайным токенам высокой энтропии, не к паролям. Сравнение выполняет
`hmac.compare_digest`; для отсутствующего token_id используется фиктивный hash.

Токен возвращается только при выдаче. Повторного чтения токена нет; при потере
нужно выдать новый и отозвать старый. Статус пользователя и отзыв проверяются
при каждом HTTP-запросе. Отключение пользователя сразу блокирует все его токены.
Повторное включение восстанавливает действие неотозванных токенов.

### Локальное администрирование

Доверенный оператор с доступом к SQLite-файлу запускает команды из корня проекта.
По умолчанию используется ASSISTANT_DB_PATH; можно передать `--database PATH`
перед именем команды. HTTP-эндпоинтов администрирования нет.

```console
python -m api.admin create-user
python -m api.admin issue-token --user-id USER_ID
python -m api.admin disable-user --user-id USER_ID
python -m api.admin enable-user --user-id USER_ID
python -m api.admin revoke-token --token-id TOKEN_ID
python -m api.admin grant --user-id USER_ID --tool echo --permission read
python -m api.admin revoke-permission --user-id USER_ID --tool echo --permission read
```

USER_ID и TOKEN_ID в примерах — заполнители, а не реальные данные. Команда
issue-token выводит исходный токен один раз в терминал: сохраните его на стороне
клиента, не перенаправляйте вывод в репозиторий или общий лог. Остальные команды
не выводят токен. Его не нужно добавлять в `.env` сервера. Новые переменные окружения
для безопасности не потребовались; `.env.example` остаётся без значений секретов.

### Граница API и совместимость

Все команды `POST /requests`, включая ping, memory и dialogue, защищены.
Без заголовка Authorization, с неверным/отозванным токеном или disabled-пользователем
возвращается `401` и `WWW-Authenticate: Bearer`. Неисправность хранилища аутентификации
даёт `503`; запрос не выполняется. `GET /health` доступен без токена и не раскрывает
данные пользователей. Origin-запросы браузера по-прежнему запрещены.

Сервер создаёт отдельный контекст пользователя на каждый запрос. Клиент может
опустить user_id либо передать свой для совместимости; чужой идентификатор даёт
`403`. session_id проверяется вместе с идентификатором пользователя из токена.
Неизвестная и чужая сессии по-прежнему возвращают одинаковую ошибку.

`memory/scoped.py` хранит факты HTTP-пользователей в user_memory по паре user_id/key.
Чтение, запись, удаление и поиск не затрагивают записи других пользователей.
Старые memory, sessions и session_messages сохранены. Для доступа к старой сессии
оператор должен явно создать пользователя с её прежним ID через
`python -m api.admin create-user --user-id LEGACY_ID` и выдать ему токен, предварительно
проверив владельца. Автоматического присвоения старых сессий или общих фактов нет.

Доверенные Python-компоненты памяти и сессий остаются доступны без HTTP-токена.
Это не граница безопасности для кода с доступом к процессу или SQLite-файлу.
Инструменты даже из Python требуют AccessContext и явного разрешения. Старые
HTTP-тесты используют временные токены; прежние сценарии сохранены, а отказы
без авторизации добавлены отдельно. Значения токенов в тестах генерируются во время
запуска, а не записываются литералами в исходники.

### Разрешения и подтверждения

У Tool есть поле permission: read, write либо sensitive. Для выполнения одновременно
нужны регистрация, enabled=True, активный пользователь и точная запись
(user_id, tool, permission) в tool_permissions. Уровни не наследуются: read не даёт
write, а разрешение одного инструмента не разрешает другой. Отсутствующее или
неизвестное разрешение, выключенный инструмент и неизвестное имя дают deny (HTTP 403).
Поля enabled, permission и confirmed в аргументах не изменяют политику.

Для sensitive с разрешением возвращается:

```json
{"ok":true,"result":{"status":"confirmation_required","tool":"danger","permission":"sensitive"},"error":null}
```

Это только состояние для будущего клиента: обработчик не вызывается, запрос
подтверждения не хранится, эндпоинта подтверждения нет. Даже confirmed=true не запускает
действие. Для dialogue такой ответ не вызывает провайдер и не записывает завершённый
ход или новую сессию. Без разрешения sensitive возвращается deny, а не подтверждение.
Никаких инструментов удаления, отправки почты, Android или платежей не добавлено.

### Журнал решений

До вызова обработчика фиксируются timestamp, user_id, имя зарегистрированного tool,
requested_permission и decision (allow/deny/confirmation_required).
При неизвестном имени записывается `<unknown>`, при неизвестном уровне — NULL:
клиент не может протащить секрет в журнал через эти поля. Аргументы, заголовки,
тексты диалога, исходные токены и их hash в audit log не записываются.
Ошибка записи аудита блокирует выполнение. allow обозначает разрешение на запуск,
а не успешное завершение действия. Неаутентифицированные HTTP-запросы отклоняются
до реестра; отдельного журнала попыток входа пока нет.

### Ограничения и следующий блок

Нет TLS, срока действия токенов, rate limiting, шифрования SQLite и защиты audit log
от изменения владельцем файла. Отзыв токенов и отключение пользователей уже доступны.
Токен даёт доступ к собственной памяти и сессиям; отдельные read/write scopes
применяются к инструментам. Доступ к файлу базы и локальной CLI считается доверенным.
Не сохраняйте секреты как обычные сообщения или факты: пользовательские данные
сохраняются буквально и не проходят автоматическое распознавание секретов.

Следующий рекомендуемый блок: постоянные запросы подтверждения с привязкой к
пользователю, сессии и точным аргументам, сроком действия, одноразовым исполнением
и защитой от повторной отправки. После этого можно подключать клиентские каналы.
